# OTP delivery: Supabase Auth hook + MSG91 (replaces the built-in Twilio sender)

Date: 2026-10-31

## Why this change exists

Supabase's hosted Auth project for VoltStop is configured with `"sms_provider": "twilio"`
(read from `GET /auth/v1/settings`). That setting lives only in the hosted project — no file in this
repository selects Twilio, and no Twilio credential is stored here. It is why every OTP investigation
so far ended at a Twilio error code we could not read from the app, and why a US sender
(`+19413927827`) was ever in the path at all: an unregistered international route is exactly the
shape of failure that produces "Auth said yes, the handset said nothing".

For an India-only product the correct shape is the Supabase **Send phone message / Send SMS hook**,
which hands the code Supabase generated to a provider we choose. The app, the SDK call and the
database are untouched: the client still calls `signInWithOtp(phone:)`, GoTrue still generates and
verifies the OTP, only the delivery leg changes.

## What is in the repository now

| Path | Role |
| --- | --- |
| `supabase/functions/send-sms/index.ts` | The Edge Function. Verifies the hook signature, reads `user.phone` + `sms.otp`, calls MSG91's OTP API, returns the envelope GoTrue expects. |
| `supabase/functions/send-sms/index.test.ts` | 6 Deno tests with a stubbed provider — signature rejection, happy path, provider error envelope, network failure, missing credentials, malformed payload. |
| `supabase/config.toml` (`[auth.hook.send_sms]`, commented) | Local-stack registration, kept off until secrets exist. |

Behaviour that matters for debugging: the function decides success from MSG91's `type` field, **not**
from the HTTP status, because MSG91 answers `200` with `{"type":"error", ...}` for an invalid
template. A rejected message therefore comes back to the app as an Auth failure instead of another
silent "Request accepted". Provider detail goes to function logs; the response body to the client
stays generic, and neither the OTP nor the full number is ever logged.

Hook contract implemented (from Supabase's Send SMS hook reference):

- Input: `{ "user": { "phone": "+91…" }, "sms": { "otp": "123456" } }`, POSTed with
  `webhook-id` / `webhook-timestamp` / `webhook-signature` headers, signed with the hook secret.
- Success: HTTP 200, body `{}`.
- Failure: non-200 with `{ "error": { "http_code": <status>, "message": "<safe text>" } }`.
- Invocation is unauthenticated (`verify_jwt = false`): the user has no session yet.

Provider call: `POST https://control.msg91.com/api/v5/otp?template_id=…&mobile=…&otp=…` with the
`authkey` header. MSG91 documents `otp` as a pass-through, so Supabase remains the code's author and
verifier — we are not creating a second, competing OTP.

## What only you can do

The code cannot be deployed from this machine: the Supabase CLI is not installed here, no Supabase
access token exists, and there is no MSG91 account or DLT registration in the project. Nothing below
was performed.

1. **MSG91 account + DLT.** Register the business as a Principal Entity with a telecom operator, get
   the Entity ID, register a 6-character Header/Sender ID (e.g. `VOLTST`), and create an **OTP
   template containing `##OTP##`** in MSG91's OTP section so it can be submitted for DLT approval.
   Approval is what makes Indian carriers stop filtering the message.
2. **Install the CLI and log in.**
   `npm i -g supabase && supabase login && supabase link --project-ref zbofzjnjgyfuistzomtt`
3. **Secrets.**
   `supabase secrets set MSG91_AUTHKEY=… MSG91_OTP_TEMPLATE_ID=…`
4. **Deploy the function with JWT verification off.**
   `supabase functions deploy send-sms --no-verify-jwt`
5. **Register the hook** in Dashboard → Authentication → Hooks → *Send phone message* (older UI:
   *Send SMS*). URI: `https://zbofzjnjgyfuistzomtt.supabase.co/functions/v1/send-sms`. Copy the
   generated signing secret into `supabase secrets set SEND_SMS_HOOK_SECRET=v1,whsec_…`, enable the
   hook, and leave the Twilio provider block in place until the hook is confirmed — Supabase requires
   a provider entry for phone auth to stay enabled, but the hook overrides its delivery.
6. **Verify.** Ask the app for an OTP on the real device, then read the function's own log
   (`supabase functions logs send-sms --project-ref zbofzjnjgyfuistzomtt`):
   `provider accepted the request, request_id=…` plus a delivered status in MSG91's SMS Logs page is
   the first end-to-end evidence this project has ever had. A `[send-sms] MSG91 rejected …` line is
   equally useful — it names the reason instead of the app guessing.
